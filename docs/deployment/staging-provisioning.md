> disk, or DNS record exists. This runbook prepares the work; it authorizes
> none of it. The prototype stays on the Supabase Free plan until the owner

date. Passing an earlier gate never authorizes a later one.

| G2 | Create and configure the staging Supabase project (sections B1 to B5) | NOT AUTHORIZED |

| G5 | DNS records for `staging.<domain>` and `api-staging.<domain>` (section E) | NOT AUTHORIZED |

Repository gate, all on the exact `main` commit to be deployed:

1. `npm ci`, `npm test`, `npm run typecheck`, `npm run typecheck:api`,
   `npm run build`.
2. Full integration suite on a **disposable** PostgreSQL 17 container
   (`npm run test:integration`).
3. The staging configuration file passes the gate:

   ```bash
   npm run staging:preflight -- --env-file <path outside the repository> [--production-ref <production project ref>]
   ```

   Prepare the file by copying `deploy/staging.env.example` outside the
   repository and replacing every placeholder. Keep its three section headers.
   Database passwords are not checked, so write `PASSWORD` in their place: the
   file then holds no secret. The preflight contacts nothing, prints no
   values, and exits `0` (ready), `1` (findings), or `2` (usage).

   It applies `config:check` to each section. It also checks that the frontend,
   the issuer, the database, and the migration connection all use one Supabase
   project; that both staging hosts share one `<domain>`; that no production
   host or production project (`--production-ref`) appears; and that every
   variable is in the section that reads it.
4. Recommended before the token-rejection smoke test (step 18): fix the
   known finding that invalid tokens return HTTP 500 instead of 401. That fix
   needs its own authorization.

## B. Supabase staging project (G1, G2)

Dashboard labels are those in use when this runbook was written. If one has
moved, find the setting by meaning, and record the label you used.

### B1. Project

| Setting | Value |
|---|---|
| Organization | The one named in the owner input sheet; record its name |
| Project | **New and separate** from production; name it, for example, `bizcaiaos-staging` |
| Region | `ap-southeast-1` (Singapore), the same region production will use |
| PostgreSQL | 17 (D-PROD-14; the migrations are validated on 16 and 17). Record the exact version |
| Database password | Generated by the operator; used only as `postgres` for section B4, then kept in the secret store |
| Compute | Small or larger (G1) |
| PITR | 14 days (G1) |

Record the **project reference** (the `<ref>` in `https://<ref>.supabase.co`).
It is an identifier, not a secret, but keep it in the staging record, not in
Git.

### B2. Auth

| Setting | Value |
|---|---|
| Email provider | **Enabled.** Do not turn off sign-ups on the email provider: on the local Supabase stack that also turned off email logins (R1 finding) |
| Allow new users to sign up | **Off.** Users are created by an administrator |
| Anonymous sign-ins | Off |
| Phone provider | Off (unless separately decided later) |
| Other providers (OAuth, SSO) | Off |
| JWT signing keys | Asymmetric (ECC P-256/ES256 preferred, or RSA) as the **current** key. If the project still has the legacy HS256 secret, migrate to signing keys, rotate the asymmetric key in, and revoke the legacy secret once nothing uses it. The API cannot verify HS256 |
| Site URL | `https://staging.<domain>` |
| Redirect URLs | Exactly `https://staging.<domain>`; no wildcards |
| Users | Created under Authentication → Users → *Add user* → *Create new user* with an email and password, auto-confirmed. The API requires the `email` claim |

The app has no OAuth, magic-link, password-reset, or invitation flows (the
frontend ignores sign-in links in the URL), so the redirect list is a
safeguard rather than a working path. Users get their password from the
administrator.

### B3. Data API

Turn the **Data API off** (Project Settings → Data API). BizcaiaOS never uses
it (D-PROD-13). The frontend calls only Supabase Auth, and Migration 019
revokes every `anon`/`authenticated` privilege in `public`.

### B4. Database roles

Create both roles as `postgres`, from the operator's own `psql` session
(direct or session-pooler connection, `sslmode=verify-full`). Set the
passwords with `\password`, which sends only a hash, so the password never
appears in SQL history. Avoid the dashboard SQL editor for this step: it can
save queries.

```sql
create role bizcaiaos_migrator login nosuperuser nocreatedb nocreaterole nobypassrls;
grant create, usage on schema public to bizcaiaos_migrator;
create role bizcaiaos_app login nosuperuser nocreatedb nocreaterole nobypassrls;
\password bizcaiaos_migrator
\password bizcaiaos_app
```

| Role | Requirements |
|---|---|
| `bizcaiaos_migrator` | LOGIN; **no** SUPERUSER, CREATEROLE, CREATEDB, or BYPASSRLS; `CREATE, USAGE` on schema `public`; owns every BizcaiaOS object; used **only** for migrations |
| `bizcaiaos_app` | LOGIN; **no** SUPERUSER, CREATEROLE, CREATEDB, or BYPASSRLS; owns nothing; gets its table, sequence, and function privileges from `db:migrate`; used **only** by the API |

`pgcrypto` must already be installed; Supabase normally installs it in schema
`extensions`. If it is missing, enable it from the dashboard (Database →
Extensions). Do **not** grant the migrator `CREATE` on the database instead.

### B5. TLS and connections

| Connection | Who uses it | Form |
|---|---|---|
| Migration (`DATABASE_MIGRATE_URL`) | Operator only, never Render | `bizcaiaos_migrator.<ref>` on the **session** pooler (port 5432), or `bizcaiaos_migrator` on the direct host `db.<ref>.supabase.co:5432`; `sslmode=verify-full` (or `require`, which the current `pg` driver treats the same way). **Never** the transaction pooler (6543): the runner needs a session for its advisory lock |
| Application (`DATABASE_URL`) | Render Web Service | `bizcaiaos_app.<ref>` on the session pooler (5432) is the default. The transaction pooler (6543) also works, because the API only uses transaction-scoped settings. Keep `DATABASE_POOL_SIZE` within the pooler's client limit for the chosen compute. `DATABASE_SSL=require` |

- Copy the pooler host from the project's *Connect* panel; do not construct
  it by hand. The direct host is IPv6-only unless the IPv4 add-on is bought,
  so Render (IPv4) is expected to use the pooler. Confirm this in step 2.
- Turn on *Enforce SSL on incoming connections* (Database → Settings).
- Both the API and the migration runner **verify the server certificate**
  against Node's trusted roots. If the first connection fails with a
  certificate-chain error, download the project's CA certificate from the
  same settings page. Then append `sslrootcert=<path>` to **both** URLs (on
  Render, store the certificate as a secret file). Never use
  `sslmode=no-verify` or `disable`; the preflight rejects them.
- Confirm in step 2 that the pooler accepts the custom roles
  (`<role>.<ref>` user names). If it does not, use the direct host for
  migrations from an IPv6-capable operator machine.

## C. Migration process (G3; steps 18 to 20 after D and E)

Operator environment:

- a **fresh clone** of the approved `main` commit, with **no `.env` file**
  (the runner fills unset variables from `.env`);
- `npm ci`;
- Linux, macOS, or PowerShell (Git Bash rewrites `/var/...` values);
- `psql` 16 or newer.

Export `DATABASE_MIGRATE_URL`, `POSTGRES_APP_USER=bizcaiaos_app`, and, for
step 14 only, `DATABASE_URL`, from the secret store into the shell. Never
paste them into chat, tickets, or this repository.

Record a UTC timestamp and the evidence for every step in the checklist.

## F. Recovery rehearsal plan (G6; not performed now)

D-PROD-07 targets: database RPO ≤ 2 minutes, RTO ≤ 4 hours, 14-day
retention; documents RPO ≤ 24 hours, RTO ≤ 4 hours. **The actual RTO must be
measured in this rehearsal, never assumed.** Until it is measured, no RTO is
claimed.

### Supabase

1. **Marker:** through the app, write a known record (for example a property
   named with the UTC time), and note the UTC time `T0`.
2. **Point-in-time restore (in place):** choose a restore point just after
   `T0`, start the restore, and record start and end UTC times. The project,
   its URL, API keys, JWT signing keys, Auth settings, and Data API setting
   are unchanged. Verify:
   - the marker exists;
   - `staging-post-migration.sql` passes;
   - `/health` and `/api/v1/me` recover.

   The **measured RTO** runs from the decision to restore until `/api/v1/me`
   succeeds.
3. **Restore to a new project (rehearsal of the worst case):** the new
   project has a **new ref, URL, publishable key, and JWT signing keys**.
   - Auth: user rows come with the database, but settings (sign-up off,
     providers, Site URL, redirect URLs) must be set again (section B2).
   - Signing keys: the API's `AUTH_ISSUER` and `AUTH_JWKS_URL` and the
     frontend's `VITE_SUPABASE_*` must change, and the Static Site rebuilt.
     Every existing session ends, so users sign in again.
   - Site URL and redirects: must be re-entered for `https://staging.<domain>`.
   - Data API: confirm it is **off** in the new project (step 5); do not
     assume the setting carried over.
   - Roles: check whether `bizcaiaos_migrator` and `bizcaiaos_app` and their
     passwords exist in the new project. If not, recreate them (B4) with new
     passwords and update `DATABASE_URL`.
   - Run `staging:preflight`, steps 2, 11 to 16, and 18 to 19 against the new
     project.

### Render

1. **Snapshot policy:** record the disk's automatic snapshot schedule and
   retention (expected daily, kept at least 7 days). Render offers no
   on-demand snapshot, so a pre-migration document backup is not guaranteed.
2. **Marker file:** upload a document, and record its storage key and SHA-256.
3. **Whole-disk restore:** restore the disk from a snapshot taken after the
   upload. This replaces the whole disk, not single files. Record start and
   end UTC times and the downtime, from the API going unavailable until
   `/health` returns `ok`. Verify the marker file's SHA-256.
4. **Consistency:** compare `select storage_key from public.documents` with
   the files under `/var/data/documents` (Render shell). List rows without
   files and files without rows. A database restored to a later point than
   the disk can reference missing files; this is an accepted limitation until
   off-host document backup (C-03, **not authorized**).

### Result

Record the measured database RTO, the measured document RTO, the data loss
window observed, and any manual steps. Compare them with the 4-hour target.
Production reliance on the targets needs this evidence first.
